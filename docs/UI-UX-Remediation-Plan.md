## Objective and authority

Resolve the audited workflow, accessibility, responsive and presentation defects in small verified slices. Preserve KhataOne's WhatsApp-first intake, CA-controlled review, ledger handoff, GST preparation and private export workflow.

This plan follows the [September 13 diagnosis](audits/ui-ux/2026-09-13-diagnosis/README.md). The [canonical findings](audits/ui-ux/2026-09-13-diagnosis/FINDINGS.md), [CSV](audits/ui-ux/2026-09-13-diagnosis/FINDINGS.csv) and [implementation inputs](audits/ui-ux/2026-09-13-diagnosis/IMPLEMENTATION_INPUTS.md) remain evidence; do not rewrite them to claim fixes. Track implementation status separately here and in [Tracker.md](Tracker.md).

The user authorized creation of this plan. This document does not claim implementation, authorize production financial mutations, or approve deployments. Existing live-account authorization supports read-only inspection. No new paid integration, framework, database or styling system is proposed.

## Baseline and evidence gate

- Audit checkout: `main` at `59b903fa696622dc81e5cfb4df9d37042c46fc7d`; 27 findings across 28 screen routes and 18 component files.
- Browser coverage: 56 public viewport observations; 97 main authenticated observations, 10 form follow-up observations, and a separate 39-observation screenshot pass. All 19 dashboard layouts were opened using an owner account. These observations are not independent performance trials.

## Execution model

Use four phases: workflow correctness; responsive/accessibility fixes; feedback and investigation; visual consistency. Phase order expresses priority, not a requirement to stall all independent work. If a workflow slice needs unavailable isolated fixtures, record its specific gate and continue a ready accessibility or containment slice. Do not mark the blocked workflow fixed because another phase shipped.

Each package below is a scope boundary, not a single large pull request. Split multi-route or multi-contract packages into independently testable changes. Keep one active implementation slice at a time; no parallel agent execution is prescribed.

Use statuses: **Planned → In progress → Locally verified → Hosted verified → Released**. Add **Blocked** with the precise dependency when necessary. Local source tests, hosted reads and released mutation behavior are different milestones. A finding closes only when its acceptance criteria and relevant environment checks pass, or an explicit product decision replaces the requirement.

## Decision register

These defaults preserve current product behavior while making ordinary implementation choices actionable. They are not claims of separate user approval for feature expansion. Ask only when dependent work reaches a genuinely unresolved product/security/accounting choice; continue independent ready slices.

| Decision | Conservative planning default | Gate or unresolved choice |
| --- | --- | --- |
| D01 — Save versus approve | Keep separate explicit Save and Approve. Expose dirty state and prevent a conflicting decision until saving succeeds | Combined save-and-approve, auto-save or altered financial transaction semantics require a separate decision |
| D02 — Date semantics | Date-only periods stay calendar strings. Asia/Kolkata calendar-day boundaries are used for Audit timestamp filters, consistent with existing display | Broader timezone policy changes still require a separate product/accounting decision |
| D03 — Return context and mobile | Preserve post-approval Ledger destination, allowlisted list context, and existing mobile actions | Changing to next-item review, queue redirect or mobile read-only scope is a product decision |
| D04 — Monthly export metric | Preserve the current query while explicitly describing its creation-month/completed-status scope | Choose creation versus completion month and timezone before changing the metric definition |
| D05 — GST provenance | Label saved generation time and current source/blocker scope; preserve saved totals | Exact historic membership may require persisted evidence. Inspect available metadata first; any schema extension or accounting interpretation requires documented review |
| D06 — Private evidence and safe detail | Preserve active membership/firm checks and short-lived signed preview URLs; display only allowlisted audit/error fields | Define allowed media/MIME fallback and metadata fields before implementation. Never expose raw payloads merely to improve discoverability |
| D07 — Visual density | Retain 56px shell, 256/68px sidebar and 8px cards as baseline while fixing proven reflow defects | Global move to screenshot candidate sizes needs concrete visual review; existing Overview proposals remain unapproved |

Mandatory correction notes, negative net-payable terminology, cess/tax buckets, direct filing, staff invites/assignment and actual firm switching are not settled by this plan. They must not enter a fixes slice implicitly.

## Test environment and fixtures

No new staging environment or paid service is required merely to start local UI work. Use isolated local fixtures/mocks for pure rendering, validation, date and interaction checks. Those tests must be explicitly labeled synthetic and must not bypass production application authorization paths.

Before mutation/storage/role integration tests, verify a genuinely isolated non-production application and database or an explicitly authorized disposable environment with sandboxed side effects. Existing previews have historically shared production Supabase; a Preview label is not isolation. Account availability does not authorize client creation, approval, exports, jobs, messages or password changes.

Minimum fixture families:

- Two firms and owner/admin/staff/viewer/revoked membership cases; cross-firm record and private-file denials.
- More than 50 review/intake records, tied timestamps, combined filters, later-page-only matches and empty-result cases.
- Unsaved draft edits, low-confidence/risky drafts, posted transactions, repeated approval and a corrected handoff; expected before/after audit state.
- Null, unavailable and legitimate zero values; read/validation/RPC failures; long firm/party/invoice strings and valid synthetic GSTIN formats.
- Text/image/PDF/audio originals, unsupported/unavailable media and expired/denied preview access.
- GST snapshots with unresolved and subsequently approved sources; month/year/leap/India-day boundary cases. Keep tax expectations tied to existing approved rules.
- Export/job queued, processing, failed and completed states; enough history and eligible periods to exceed existing list limits; safe and sensitive metadata fixtures.

Do not use a real account to simulate outages by changing memberships, corrupting data or disabling production services. Record unavailable integration checks as blocked rather than treating mocked success as hosted verification.

## Slice definition of done and release discipline

Every implementation change must state: finding IDs, reproduced starting behavior, scope and excluded adjacent work, source files, data/role/audit implications, loading/empty/error/pending/success states, test fixtures/results, and unresolved assumptions.

Run relevant existing tests and meaningful behavior checks for the actual change. Source-pattern checks alone cannot close workflow or accessibility findings. Run lint/typecheck/build for implementation changes. For UI changes, inspect affected consumers at 320, 390, 768, 1024, 1280, 1440 and 1920 CSS pixels as applicable, including both sidebar states for width-sensitive layouts. Verify true 200% browser zoom, keyboard focus/return and applicable screen-reader/error behavior; record exact omitted combinations.

Before release, confirm the candidate commit, deployment identity and any required RPC/migration coupling. Preserve no-store/privacy behavior, fresh firm/role verification, RLS, original/raw evidence, atomic handoff/audit, posted immutability and private artifacts. Do not introduce region, prefetch, global-cache or worker-policy changes as an incidental UI optimization.

Prepare a concrete diff, evidence and rollback path before any final release approval step. Prefer independently releasable code slices. A database-dependent change needs coordinated compatibility and rollback review; reverting UI must not reopen prohibited direct writes or remove retained financial evidence. Production deployment remains a separately authorized action.

After each slice, update this package's status and Tracker with what actually passed. After a release, perform read-only hosted regression checks and record its exact version. Close findings individually; do not declare the whole application fixed from one owner account, passing build or screenshot.
