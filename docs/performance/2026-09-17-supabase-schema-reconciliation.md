# Supabase schema reconciliation — 2026-09-17

Target: the active KhataOne Supabase project whose reference matches
`NEXT_PUBLIC_SUPABASE_URL` in this workspace. The initial live checks were read-only;
the controlled migration release described below subsequently changed schema
and migration history.
All 37 repository migrations also replayed successfully in a separate temporary
local Supabase database; that does not prove they previously ran in production.

The sampled operational tables were each under 224 kB in PostgreSQL's total
relation-size estimate at the time of inspection. Missing indexes remain a
scaling issue, but this snapshot alone does not establish that they cause the
currently reported delay. The absent RPCs do explain the observed `PGRST202`
and compatibility fallback. The catalog comparison identifies concrete drift;
it cannot prove every historical data backfill ran, though the current
approved-to-ledger invariant was checked.

## Release boundary and outcome

At the initial state, a blanket `db push` would have replayed all 37 files over
a populated database. Marking all 37 versions as applied would also have
misstated the live database: three migrations had visibly missing objects, and
the legacy `clients` table differed from the clean replay. Supabase's
`migration repair` edits tracking history without running SQL.

After comparing the clean replay with the live catalog and sampling the
historical data effects, 34 versions with verified live effects were recorded
as applied using `migration repair`. This repaired history only; it did not
rerun their SQL or prove every historical data backfill. The two index versions
and `20260913110000` remained pending. The observed legacy client-column/check
drift remains documented above, not silently changed.

An isolated temporary CLI project contained the 34 recorded versions and the
existing `20260913110000_complete_dashboard_filtered_results.sql`, excluding
both index migrations. Its `db push --dry-run --skip-vault` listed exactly that
one RPC file. The live push applied it. `migration list` then showed 35 applied
and the two index files pending. An authenticated one-row preflight resolved
both `search_review_queue` and `search_whatsapp_inbox` without `PGRST202`.

The first post-release catalog check found that Supabase's explicit default
`anon` EXECUTE grants survived the original migration's `REVOKE ... FROM public`.
The two functions are security-invoker and check firm membership, but their
intended authenticated-only grant was not enforced. A forward migration,
`20260917060000_restrict_dashboard_search_rpc_execute.sql`, revokes execution
from `public, anon` and preserves `authenticated` execution. A separate isolated
dry run listed only that file, then the live push applied it. Catalog checks now
show `anon_execute=false`, `authenticated_execute=true`, and
`security_definer=false` for both functions; the authenticated preflight still
passes. Migration history now has **36 applied and two pending** versions.

The two index migrations still need separate query-plan and rollout review; they
should not be assumed to solve current latency on these small tables. Keep
`clients.phone` and missing checks visible as legacy drift. No customer rows
or financial records were changed by this release. The schema and migration
history were changed only for the two RPC functions, their grants, and the
reviewed migration baseline. A three-sample hosted browser check completed,
but does not establish a speed improvement; see
[the post-release sample](2026-09-17-post-rpc-mobile-sample.json).

Because the two remaining migrations predate the now-applied RPC versions, a
normal repository `db push --dry-run` refuses their ordering. A read-only
`--include-all --dry-run --skip-vault` lists exactly those two index files. Do
not run the corresponding live `--include-all` push until authenticated plans
and rollout impact have been reviewed.

The CLI schema-dump `--dry-run` mode prints a temporary database login in its
command preview; avoid using or sharing that output during further analysis.
